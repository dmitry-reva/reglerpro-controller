### Находка 79: числа, которых нет у контроллера

Числа котла становятся недоступными, если приложение ReglerPro показывает этот параметр иначе. Правила взяты из `functions.js`:

| Параметр | Когда доступен |
|---|---|
| Шнек (`shn_roz_vkl`, `shn_roz`, `shn_uga_vkl`, `shn_uga`) | только у «авто»-котлов |
| `vent_min` | только у остальных котлов |
| «Коррекция t° воды» (`korect_`) и «Время угасания» (`time_ugas`) | только если `korect_20 > 0` |
| `servo_cooler` | только при ненулевом значении |
| Остальные | если значение пришло от контроллера |

Значение недоступного числа остаётся в состоянии, поэтому автоматизации его по-прежнему читают. Числа расписания эти правила не затрагивают.

Для котла с прошивкой 291023 («авто») ожидается: `vent_min` недоступен, `servo_cooler` пока недоступен, потому что значение равно 0; шнек, `korect_` и `time_ugas` доступны.

### Находка 80: два новых числа

- **«Заслонка вентилятора»** (`servo_cooler`) — 1–99 %.
- **«Коррекция датчика температуры»** (`korect_dt`) — −15…15 °C с шагом 0,5, у каждого датчика.

`servo_cooler` уже есть в профилях котла как допустимое значение. `korect_dt` в профили не входит: она относится к датчику, а не к контроллеру. `korect_dt` записывается без сдвига на 20, как в приложении; у `korect_` сдвиг остаётся.

### Наблюдение 83

В приложении кнопка «Климат» скрыта для прошивки `vers = 201742`. В Home Assistant у такого контроллера климатические сущности остаются, но могут ничего не показывать. Изменений пока нет, это наблюдение в аудите.

# ReglerPro Controller — релиз 1.7.0

**Тип:** проверка входа и выбор дома при подключении  
**Дата:** в предоставленных материалах не указана

## ✨ Что нового в 1.7.0

Окно подключения теперь проверяет вход через `login_user` и предлагает дома из `get_data_sets`. Форматы ответов взяты из кода приложения (`reglog.js`, `sets.js`), на живом сервере не проверялись.

### Как работает добавление интеграции

1. **Первый шаг:** сервер, логин и пароль. Номер дома необязателен.
2. **Проверка входа** запросом `login_user`, как в приложении. Если сервер отклоняет вход и поясняет причину, текст показывается в ошибке. Он очищается от разметки и от логина с паролем. Если пояснения нет, остаётся «Неверный логин или пароль».
3. **Дома** берутся запросом `get_data_sets`:
   - один дом выбирается сам;
   - несколько домов дают список «название (номер)»;
   - введённый вручную номер должен быть среди ваших домов, иначе ошибка «этого номера нет среди домов учётной записи» со списком ваших домов;
   - если домов нет — сообщение «У этой учётной записи нет домов»;
   - если список домов получить не удалось, остаётся прежнее поле для ручного ввода номера.
4. **Повторная авторизация** проверяет только логин и пароль, без запроса устройств.

Название записи теперь содержит название дома. Данные записи (`url`, `login`, `password`, `home_id`) не изменились, существующие записи продолжают работать.

Проверка принадлежности дома закрывает находку 74 со стороны интеграции: нельзя случайно или намеренно подключить чужой номер через окно настроек. Сервер по-прежнему не проверяет членство при `get_all_dev`, это его проблема. На сценарий «образец профиля для пользователей с другим оборудованием» это не влияет: профили от номера дома не зависят.

### Что неизвестно

- Что `login_user` отвечает на неверный пароль и что кладёт в поле `text`.
- Совпадают ли номера в списке домов с номером, который принимает `get_all_dev`. После выбора дома интеграция всё равно проверяет устройства: при расхождении будет «Нет устройств».
- Номера домов бывают отрицательными (в `script.js` есть примеры вида `-1002211493629`). Это учтено, номера не проверяются на «только цифры».

Если ответы окажутся другими, интеграция не сломается: список домов вернётся к ручному вводу, а ответ `login_user` другого вида даст «неожиданный ответ» с выдержкой.

## 🔁 Совместимость

Формат профилей и `unique_id` сущностей не меняются. После обновления:

1. Распакуйте `kotel_1.7.0.zip` поверх репозитория с заменой файлов.

## ✅ Что проверить на живом Home Assistant

Для проверки можно добавить запись заново, например второй раз для того же дома, и затем отменить: дубль отклоняется до создания записи.

1. Неверный пароль: какой текст показывает сервер.
2. Верный вход без номера дома: один дом выбирается сам, несколько дают список.
3. Номер дома, которого нет среди ваших домов.
4. Повторная авторизация с верным и неверным паролем.
5. По желанию: в журнале уровня `debug` для `custom_components.kotel.api` виден вид ответов `login_user` и `get_data_sets`.

## ✨ Что нового в 1.6.1

### Сверка с `functions.js`

Загружен свежий вариант (`site`, v1.1 от 16.02.2026). Большая часть отчёта внешнего разработчика касается браузера, а не клиента API.

**Согласуется, правок не потребовалось:**

- **Повторы запросов.** Приложение повторяет только `get_all_dev`, а команды отправляет один раз. Клиент для записи делает то же: на другой сервер переходит только если запрос заведомо не дошёл. Старый безусловный повтор команд не нужен.
- **Остальное:** `add_device`, ответы `get_climat_sensors`, пропуск элементов без `id_name`, логирование без логина и пароля.
- **Формула охлаждения/нагрева.** `tstatNow` в приложении трактуется так же, как в интеграции, поэтому находка 75 закрыта.

**Исправлено:**

- **Диапазоны.** Максимум для `shn_roz_vkl` и `shn_uga_vkl` в приложении 600, было 300. Профиль со значением выше 300 отклонялся бы. Остальные 10 параметров котла и температура климата совпали.
- **Порог «в сети» у датчика:** было 300 с, в приложении 1800.
- **«В сети» у контроллера.** В приложении он считается подключённым не только при `mqtt_online = 1`, но и при `0`, если с обрыва прошло меньше 600 с. Это добавлено в новое поле `online`. Сенсор «Соединение» и проверка перед применением профиля используют его, а исходное `mqtt_online` сохранено.
- **Один испорченный элемент списка** больше не останавливает опрос остальных устройств. В журнал пишется одно предупреждение.

### Случай «не подтверждено 1»

Причину установить не удалось: в сообщении не видно, какое значение не подтвердилось. Само значение могло потеряться, а могло записаться и не отразиться в `get_big_contr`. Поэтому сделано три вещи:

1. Сообщение кнопки теперь называет значения: «boiler.temp_w_min (ожидалось 35, получено 40)».
2. Приложение проверяет запись другим запросом, `get_big_contr_check`. После основного ожидания интеграция проверяет неподтверждённые параметры котла тем же запросом.
3. Всё, что осталось неподтверждённым, записывается ещё один раз и проверяется снова. Это безопасно, потому что команды установки значения повторяемы, а переключатели в профили не входят.

`get_big_contr_check` на живом сервере не проверялся: предполагается, что формат ответа такой же, как у `get_big_contr`. Если запрос не сработает, ошибка игнорируется и остаётся повторная запись.

## ✨ Что нового в 1.6.0

В версии 1.6.0 обновлена организация runtime-данных и жизненный цикл служб по паттернам Home Assistant. Данные клиента API и координатора привязаны к записи интеграции, а команды платформ управления выполняются с заданным ограничением параллельности.

### Находка 18: `runtime_data`

- Клиент API и координатор теперь хранятся в `entry.runtime_data` вместо отдельной записи в `hass.data` для каждого config entry.
- Сущности используют API-клиент координатора; у конструкторов больше нет параметра `entry_id`.
- Профильный менеджер остаётся общим для всех записей и лежит в `hass.data`.
- Для платформ Home Assistant используются значения `Platform`, для интеграции задана схема `CONFIG_SCHEMA`, допускающая настройку только через config flow.

### Находка 51: `PARALLEL_UPDATES`

- Для `switch`, `number`, `select`, `text`, `button` и `climate` задано `PARALLEL_UPDATES = 1`.
- Для `sensor` задано `0`.
- Быстрые команды одной платформы теперь выполняются по очереди.
- Профили пишут напрямую через клиент и этим ограничением не затронуты.

### Находка 70: службы в `async_setup`

- Менеджер профилей и все 9 служб создаются один раз при загрузке интеграции, а не при настройке записи.
- Без загруженной записи службы отвечают «Интеграция Kotel ещё не загружена» или «Контроллеры Kotel не найдены», а не падают с `KeyError`.
- Добавлены `CONFIG_SCHEMA` и `Platform` вместо строк, функции снятия служб удалены.
- При выгрузке записи платформы снимаются, менеджер профилей теряет ссылку на запись, API-клиент закрывается.

### Окно «Добавить датчик»

У незагруженной записи окно теперь завершается сообщением `not_loaded` вместо ошибки. Ключ есть в `translations_additions/`, переводы нужно слить заново.

# ReglerPro Controller — релиз 1.5.2

**Дата:** 2026-11-16  
**Тип:** повторная авторизация и повышение надёжности

## ✨ Что нового в 1.5.2

### Повторная авторизация

- При отклонении сохранённых учётных данных Home Assistant предлагает ввести новый пароль. После проверки запись перезагружается автоматически; повторно добавлять интеграцию не требуется.
- При первом опросе отказ авторизации сразу запускает повторную авторизацию. Если запись уже успешно работала, один отказ считается возможным временным сбоем; повторная авторизация запускается после второго отказа подряд.
- Ошибки авторизации при добавлении записи и повторной авторизации показываются отдельно от ошибок соединения и некорректного ответа сервера.

### Обработка ответов API и таймаутов

- Ответы неправильного типа больше не трактуются как пустой список устройств: неожиданный ответ определяется отдельно, а короткая выдержка доступна в сообщении об ошибке.
- Отказы авторизации распознаются по HTTP 401/403 и характерному ответу API; клиент не пытается перейти на другой сервер с теми же неверными учётными данными.
- Отсутствие ответа при запросах чтения имеет отдельное сообщение. Команды записи при неопределённом результате не повторяются на другом сервере, чтобы не выполнить переключение или изменение дважды.

### Скрытие данных в диагностике

- Диагностический отчёт обезличивает логин, пароль, ID дома и идентификаторы устройств, в том числе внутри вложенных значений и ключей.
- Выдержки неожиданных ответов API очищаются от логина и пароля перед показом пользователю и записью в журнал.

## 🔁 Совместимость

Миграция профилей и настроек не требуется. Идентификаторы сущностей и сценарии автоматизации не меняются. При отклонении пароля используйте форму повторной авторизации; после успешной проверки интеграция перезагрузится автоматически. Поддержка основного и резервных серверов сохраняет правило: команда, которая могла дойти до сервера, не отправляется повторно.

## 📦 Файлы релиза

| Файл | Что изменилось |
|---|---|
| `api.py`, `coordinator.py` | распознавание отказа авторизации, неожиданных ответов и таймаутов; безопасная логика повторов |
| `config_flow.py`, `__init__.py` | повторная авторизация и перезагрузка записи после проверки нового пароля |
| `diagnostics.py` | сокрытие учётных данных и идентификаторов в отчёте |
| `strings.json`, `translations/en.json`, `translations/ru.json` | переводы шагов и сообщений повторной авторизации и ошибок |
| `tests/test_reauth_and_responses.py`, `tests/test_real_server_data.py` | проверки авторизации, ответов API и обработки секретов |
