# ReglerPro Controller — релиз 1.4.1

**Дата:** 2026-10-24
**Тип:** упаковка и CI
**Требования:** Home Assistant 2026.3.0 и новее
**После обновления:** перезапуск Home Assistant

Релиз переводит распространение через HACS на zip-архив и автоматизирует его
сборку. Код интеграции, сущности, переводы и дашборды не менялись.

---

## 📦 Что нового в 1.4.1

### HACS zip-релиз

- `hacs.json`: `"zip_release": true`, `"filename": "kotel.zip"`.
- HACS скачивает asset `kotel.zip` из GitHub Release и распаковывает его
  **в `/config/custom_components/kotel`**. Поэтому в корне архива лежат
  `__init__.py`, `manifest.json`, `brand/`, `translations/` и остальные файлы
  интеграции — без префикса `custom_components/kotel/`.
- `content_in_root` остаётся `false`: HACS по-прежнему находит интеграцию в
  `custom_components/kotel` в git-дереве.

### Автоматическая сборка

- Добавлен `scripts/build_release_zip.py`:
  - собирает детерминированный `dist/kotel.zip`;
  - исключает `__pycache__`, `*.pyc`, `.DS_Store`;
  - проверяет `manifest.json` в корне, отсутствие префикса
    `custom_components/` и совпадение версии с тегом.
- Добавлен workflow **`Release zip`** (`.github/workflows/release.yml`):
  - запускается при публикации GitHub Release;
  - проверяет код (`compileall`, `check_i18n`, unit-тесты);
  - собирает `kotel.zip` с проверкой версии;
  - прикладывает asset к релизу через `gh release upload --clobber`.
- Ручной запуск: Actions → **Release zip** → Run workflow → существующий тег.
- Локальная сборка:
  ```bash
  python scripts/build_release_zip.py --output dist/kotel.zip --expected-version v1.4.1
  ```

---

## ⚠️ Важно для релизов

- Начиная с 1.4.1 **каждый релиз обязан содержать `kotel.zip`**. Если asset
  отсутствует, HACS не установит/не обновит эту версию.
- Старые теги используют собственный `hacs.json`; задним числом менять их
  поведение не нужно.
- Workflow запускается после публикации релиза, поэтому asset появляется
  через несколько секунд. Если HACS уже успел запросить релиз, обновите
  список в HACS.
- При переходе с 1.4.0 сразу публикуйте 1.4.1. Если HACS попытается
  установить 1.4.0 уже после появления `zip_release` в ветке по умолчанию,
  приложите `kotel.zip` к 1.4.0 вручную (архив из файлов этого тега) или
  сначала выпустите 1.4.1.
- Если тег не совпадает с `version` в `manifest.json`, workflow завершится
  ошибкой — это защита от случайного релиза.

  контроллера не блокирует остальные.
- **Нормализация `mqtt_online`**: число `1` больше не превращается в
  `offline`.
- **Понятные ошибки записи** в `number` и `switch` (`HomeAssistantError`).
- **`kotel.send_command` зарегистрирован** — больше не «фантомная» служба.
- **Диагностика записи** (`diagnostics.py`): отчёт без логина и пароля.
- Общий базовый класс `KotelEntity`: единые `device_info`, `available`,

# ReglerPro Controller — релиз 1.3.1

> Историческая версия. Ограничения ниже (`scan_interval`, `send_command`,
> переводы) исправлены в 1.4.0; раздел оставлен для истории обновлений.

**Дата:** 2026-10-23
**Тип:** функциональное обновление
**Требования:** Home Assistant 2026.3.0 и новее
**После обновления:** перезапуск Home Assistant

Главное в релизе — **профили котла и профили климата теперь независимы**. Профиль котла («Отпуск») и профиль климата («Расписание 7/7 — солнечные дни» или «Расписание 7/7 — пасмурные дни») выбираются, применяются и откатываются отдельно, не затрагивая друг друга.

---

## ✨ Что нового в 1.3.1

### Два типа профилей

- **Профиль котла** (`boiler`) — 11 настроек котла. **Профиль климата** (`climate`) — режим климат-контроля, целевая температура и расписание; по желанию выбранный датчик.
- Для каждого типа **свой список, выбор, последнее применение и откат**. До 20 профилей каждого типа на контроллер; имена котла и климата не пересекаются (профиль «Зима» может быть и у котла, и у климата).
- **Новые сущности для климата** (на каждый контроллер):

  | Сущность | Назначение |
  |---|---|
  | `select` «Профиль климата» | выбор профиля климата |
  | `text` «Имя нового профиля климата» | имя для сохранения |
  | `button` «Сохранить профиль климата» | сохранить режим, цель и расписание |
  | `button` «Обновить профиль климата» | перезаписать выбранный профиль |
  | `button` «Применить профиль климата» | записать выбранный профиль |
  | `button` «Отменить применение (климат)» | вернуть расписание до применения |
  | `sensor` «Активный профиль климата» | профиль, совпадающий с текущим климатом |

  Сущности котла получили названия «Профиль котла», «Имя нового профиля котла», «Сохранить / Обновить / Применить профиль котла», «Отменить применение (котёл)», «Активный профиль котла». **Идентификаторы существующих сущностей не меняются.**

- **Профиль климата сохраняет расписание только активного режима** (7/7, 5/2 или 4/1/2): профиль «7/7 — солнечные дни» не затрагивает наборы 5/2 и 4/1/2. В режиме постоянной температуры сохраняются режим и цель. Параметр `all_schedules` сохраняет все наборы.
- **Защита обновления.** Профиль климата запоминает режим; «Обновить профиль климата» в другом режиме отклоняется с пояснением, чтобы в профиль 7/7 не попали значения 5/2.
- **Применение профиля климата не включает и не выключает климат-контроль**: записываются только режим, цель и расписание.

### Службы

- Во всех службах профилей появился параметр **`kind`** (`boiler` или `climate`). Если он не указан, тип определяется по областям (`save_profile`) или по имени профиля (`apply_profile`, `delete_profile`, `rename_profile`); при неоднозначности требуется явный `kind`. `undo_apply` по умолчанию относится к котлу.
- `save_profile`: области по умолчанию — `boiler` для котла и `climate` + `schedule` для климата; новый параметр `all_schedules`. Смешивать области котла и климата в одном профиле больше нельзя.
- `list_profiles`: профили котла остаются на верхнем уровне ответа (как в 1.3.0), добавлены блоки `boiler` и `climate`, у профилей — поле `kind`.
- `export_profiles` и `import_profiles`: фильтр по `kind`; в ответе экспорта счётчики `boiler` и `climate`; в ответе импорта у профилей указан тип.
- События `kotel_profile_saved` и `kotel_profile_applied` содержат `kind`.

### Экспорт и импорт

- Формат файла **версии 2**: у каждого профиля поле `kind`, у профилей климата — `mode`. Файлы версии 1 (из 1.3.0) импортируются; профиль со смешанным содержимым автоматически делится на профиль котла и профиль климата с тем же именем.
- В окне «Настроить» профили подписаны «Котёл · имя» и «Климат · имя». Конфликты имён при импорте проверяются внутри своего типа.
- Если два экспорта выполнены в одну секунду, файлы не перезаписываются (суффикс `_2`, `_3`).

### Дашборд

- Карточка «Профили настроек» разделена на **«Профили котла»** и **«Профили климата»**.

### С версии 1.3.0

## ⚠️ Известные особенности

- **Интервал опроса** фиксирован (30 секунд): параметр `scan_interval` из окна настроек сохраняется, но пока не применяется.
- **Служба `kotel.send_command`** описана в `services.yaml`, но не зарегистрирована.
- **Порядок записи уставок.** Неизвестно, требует ли контроллер, чтобы минимальная уставка была меньше максимальной; при значительном сдвиге обеих уставок сначала выполните `apply_profile` с `dry_run: true`.
- **Расписания 5/2 и 4/1/2.** Ключи этих наборов на сервере появляются после первой записи; поведение сервера при записи «с нуля» проверяется.
- **Профиль климата не управляет включением климата.** Если климат-контроль выключен, режим и расписание записываются, но не действуют до включения.
- **Задержка подтверждения.** Значения настроек котла приходят от устройства с задержкой; при медленной связи параметры могут попасть в список «не подтверждено», хотя уже применены.
- **Новые устройства**, добавленные в облако после запуска, появляются после перезагрузки интеграции.
- Смысл значений аварий и ошибок выведен из названий параметров; они отображаются как «нет» / «да» (без `binary_sensor`).
- Индикаторы «ШНЕК» и «НАСОС» в примере дашборда не заполняются: прошивка не отдаёт отдельного признака их работы.
- Файл профилей остаётся в `.storage/` при удалении интеграции из интерфейса.

## 📋 План

- Аварийные параметры как `binary_sensor` (`device_class=PROBLEM`).
- Применение `scan_interval` из окна настроек.

## 1.2.0

### Климат-контроль

- **Термостат (`climate`)**: режимы `Выкл`, `Нагрев` (постоянная температура), `Авто` (расписание); пресеты «Расписание 7/7», «Расписание 5/2», «Расписание 4/1/2»; целевая температура 5–40 °C с шагом 0,5 (в режиме расписания только чтение); действие по `tstatNow` (`0` — нагрев, `1` — охлаждение).
- **Выбор датчика климат-контроля** (`select`).
- **48 полей расписания** (`number`, категория «Конфигурация»): время начала и температура для 4 периодов в 6 наборах. Границы времени зависят от соседних периодов.
- Команда `climat_on_off` на сервере — переключатель, поэтому перед включением и выключением данные обновляются и команда отправляется только при необходимости.
- Описание протокола: [docs/CLIMATE.md](./docs/CLIMATE.md).

### Диагностика

- Диагностические сенсоры по параметрам, которые отдаёт прошивка: версия, вентилятор, аварии и ошибки, шнек, климат, выносной датчик, значения климат-контроля.
- Сводный сенсор **«Диагностика параметров»** с атрибутами `params`, `params_raw`, `params_format`, `climate`, `tstatArr`, `tempUstNowTstate`, `raw_keys`.

### Удалено

Интеграция больше не создаёт 8 сенсоров, по которым прошивка не отдаёт данных; те же параметры доступны как `number`-сущности. Устаревшие записи удаляются из реестра автоматически.

| Параметр | Сенсор |
|---|---|
| `vent_max`, `vent_min` | Вентилятор (max), Вентилятор (min) |
| `nasos_t` | Температура насоса |
| `produv_time`, `produv_interval` | Время продувки, Интервал продувки |
| `time_ugas` | Время угасания |
| `korect_` | Коррекция температуры |
| `servo_cooler` | Заслонка вентилятора |

Если автоматизации или дашборды ссылались на эти `sensor.*`, замените их на `number.*`.

### Исправления

- `sensor.py`: класс `KotelClimateModeSensor` был вложен в другой класс, из-за чего платформа `sensor` не загружалась (`IndentationError`).
- Сенсор `tstatNow`: убраны несуществующий `SensorDeviceClass.STATE`, неподдерживаемый `extra_state_attributes` и словарь вместо строки в `icon`.
- Парсер `params`: дробные значения (`45.5`) больше не превращаются в `0`; отсутствующий `tstatNow` даёт `None`, а не «нагрев»; при отсутствии `korect_20` параметр `korect_` не равен `-20`; проверяется, что JSON — это список; порядок определения формата совпадает с `functions.js`.
- `is_kotel_auto` и `sost_rab_text` не падают на `None` и строковых значениях.
- Флаги климат-контроля из API (`"0"`, `"false"`) разбираются корректно.
- Пустой ответ `get_big_contr` больше не затирает данные контроллера: используется элемент из `get_all_dev`.
