# Аудит интеграции ReglerPro Controller для Home Assistant

**Дата:** 23 октября 2026  
**Версия на входе:** 1.3.1  
**Версия после изменений:** 1.4.0  
**Предмет:** `custom_components/kotel`, дашборды, документация, переводы.  
**Метод:** статический разбор всех файлов интеграции, сверка документации с
кодом и `functions.js` / `climate.js`, проверка JSON и Python, юнит-тесты
парсера. Живой Home Assistant и облако ReglerPro в ходе аудита не
использовались, поэтому выводы о поведении сервера опираются на код и
документацию, а не на новый сетевой эксперимент.

---

## 1. Кратко

Интеграция зрелая для кастомного проекта:

* устойчивый парсер `params` с двумя форматами и защитой от мусора;
* продуманная работа с климатом, включая «переключающую» команду
  `climat_on_off`, очередь команд и проверку состояния перед отправкой;
* профили с миграцией схемы, валидацией, откатом, экспортом/импортом;
* подробная документация и пример дашборда на штатных карточках;
* нет внешних Python-зависимостей, есть `brand/`, HACS-манифест и переводы
  окна настройки.

Главные системные пробелы на входе:

1. **Не выполнялись обещания, записанные в README**: интервал опроса не
   применялся, служба `send_command` была описана, но не зарегистрирована.
2. **Сущности были непереводимыми**: русские названия зашиты в Python,
   переводы покрывали только config/options. Это противоречит стандарту
   Home Assistant и делает английский интерфейс невозможным.
3. **Дублирование инфраструктуры сущностей**: `device_info`, `available`,
   подписка на координатор и `unique_id` повторялись в семи платформах,
   производитель устройства был указан как «Kotel», а не «ReglerPro».
4. **Слабые места надёжности**: последовательные запросы к контроллерам,
   отсутствие `unique_id` у config entry, создание пустой записи при
   `home_id` без устройств, необработанные ошибки API в `number`/`switch`,
   сравнение `mqtt_online` только со строкой `"1"`.
5. **Дашборд-пример был единственным** и содержал устаревшие комментарии
   (`0/1` вместо `да/нет`), разнородные ID и неточный заголовок gauge.

В версии 1.4.0 исправлены пункты 1–4 и добавлены три новых варианта
дашборда, каталог сущностей, стандарт переводов, диагностика, тесты парсера
и проверка переводов. Пункты, требующие ломающих изменений (бинарные сенсоры,
английские значения состояний и пресетов), вынесены в план 2.0.

## 2. Что сделано хорошо

| Решение | Почему это важно |
|---|---|
| `DataUpdateCoordinator` | единая точка опроса, `last_update_success`, нормальная интеграция с HA |
| `params_parser` | два формата, `None` вместо ложного нуля, защита от NaN/мусора |
| `climat_on_off` как переключатель | перед командой данные обновляются, команда не повторяется вслепую |
| `asyncio.Lock` в термостате | команды климата не перемешиваются |
| профили | миграция схемы, проверка диапазонов, безопасный порядок времени, откат, экспорт/импорт |
| `Brand`-папка | иконка и логотип в интерфейсе HACS/HA |
| документация | `CLIMATE.md` и `PROFILES.md` действительно описывают протокол и поведение, а не только UI |
| отсутствие зависимостей | установка не требует `pip`, меньше точек отказа |

## 5. Переводы и унификация сущностей

### Что было

* `strings.json` и `translations/*.json` содержали только `config` и
  `options`; `strings.json` был на английском, `ru.json` — на русском.
* Названия сущностей — русские строки в Python; `has_entity_name` не
  использовался.
* `services.yaml` содержал русские `name`/`description`, поэтому службы
  нельзя было перевести.
* Состояния `да/нет`, `Остановлен`, `Нагрев`, `Расписание 7/7` — русские
  значения, которые нельзя перевести без миграции.

### Что сделано

* Добавлен `KotelEntity` — единая база: `device_info`, `available`,
  подписка, `unique_id`, `has_entity_name`.
* Все платформы переведены на `translation_key`; в `strings.json`,
  `en.json`, `ru.json` — 109 сущностей и 9 служб.
* `services.yaml` очищен от `name`/`description`; они перенесены в
  переводы по стандарту HA 2023.8+.
* Добавлены переводы состояний для enum-сенсоров и пресетов термостата;
  русские значения сохранены для совместимости.
* Добавлены [ENTITIES.md](./ENTITIES.md) — единый каталог сущностей,
  [I18N.md](./I18N.md) — глоссарий и правила.
* Добавлен `scripts/check_i18n.py` — проверка паритета ключей и служб.

### Что осталось на 2.0

1. `binary_sensor` для аварий/ошибок вместо enum `да/нет`.
2. Английские стабильные значения состояний и пресетов + миграция.
3. `icon-translations` и `exception-translations`.
4. Полный отказ от русского текста в Python (включая сообщения исключений —
   через `translation_domain`/`translation_key`).

## 6. Дашборды

### 6.1. Существующий дашборд

`dashboards/kotel_dashboard.yaml` — `picture-elements` с живой панелью
контроллера, кнопкой «F», термостатом, gauge, графиком, профилями и
диагностикой. Сильные стороны: без HACS, узнаваемая панель, хорош на
настенном планшете. Слабые: один view, много `conditional`-элементов,
жёсткие ID, комментарии `0/1` устарели, заголовок «Температура воды» у
gauge, который показывает температуру датчика климата.

### 6.2. Предложенные варианты

| Файл | Стиль | Зависимости | Для чего |
|---|---|---|---|
| `kotel_dashboard_sections.yaml` | современные Sections, native cards | нет | универсальный, телефон + планшет |
| `kotel_dashboard_mushroom.yaml` | Mushroom | HACS: Mushroom | компактный «популярный» вид, быстрые действия |
| `kotel_dashboard_tablet.yaml` | Kiosk/настенный планшет | нет (опционально kiosk-mode) | большие кнопки, панель контроллера, минимум лишнего |
| `kotel_dashboard_mobile.yaml` | одна колонка, compact | нет | телефон, только главное |

Почему именно они:

* **Sections** — рекомендуемый HA-подход с 2024.3: адаптивная сетка,
  `heading`, `tile`, нормальное поведение на телефоне. Лучший выбор по
  умолчанию.
* **Mushroom** — самый популярный HACS-стиль; даёт «живые» карточки
  температуры/статуса и хорошо смотрится на телефоне. Требует установки
  Mushroom, поэтому вынесен отдельно.
* **Tablet/Kiosk** — сценарий «панель на стене»: крупные элементы,
  `picture-elements`, подтверждение старта/остановки, скрытая диагностика.
* **Mobile** — быстрый доступ к температуре, старту/стопу и термостату
  без прокрутки.

Дополнительно можно добавить `statistics-graph` по температуре воды и
`apexcharts-card` для долговременных трендов, но это уже отдельный
аналитический view, а не «популярный» шаблон.

## 9. Риски текущего изменения

| Риск | Оценка | Смягчение |
|---|---|---|
| `has_entity_name` меняет отображаемые имена | низкий | `unique_id` и `entity_id` не меняются; в README добавлено пояснение |
| Переводы служб не подхватятся, если HA ниже 2023.8 | низкий | требование 2026.3.0, переводы поддерживаются |
| `services.yaml` без `name` на старых версиях | низкий | то же требование |
| Параллельный опрос увеличивает нагрузку на облако | низкий | число контроллеров обычно 1–2; таймаут 15 с |
| `send_command` расширяет поверхность управления | средний | служба требует авторизации HA; в описании предупреждение; не включена в дашборды |
| Ошибка в `KotelEntity` MRO | низкий | `compileall` + базовые тесты; рекомендуется прогнать в живом HA |

## 10. Приложение: проверки

```bash
python -m compileall -q custom_components
python scripts/check_i18n.py
python -m unittest discover -s tests -v
```

Ожидаемый результат:

* `compileall` — без ошибок;

* `unittest` — 13 тестов парсера, OK.

проверить загрузку платформ, переводы в русском и английском интерфейсе,
применение профиля, термостат и опрос с интервалом из options.
