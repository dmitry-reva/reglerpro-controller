# Аудит интеграции ReglerPro Controller для Home Assistant

**Дата редакции:** 14 ноября 2026 (предыдущая редакция — 23 октября 2026)  
**Версия на входе первого аудита:** 1.3.1  
**Версия, к которой относится эта редакция:** 1.4.8 (`manifest.json`)  
**Проверено на действующем Home Assistant:** 1.4.6 (см. раздел 10)  
**Предмет:** `custom_components/kotel`.  
**Метод:** статический разбор кода, сверка `strings.json` и `services.yaml`
с кодом, юнит-тесты на заглушках Home Assistant и прогон изменений 1.4.6 на
действующей установке (раздел 10). Прогона 1.4.7 и 1.4.8 (несколько серверов и
шаг «Серверы») на живом Home Assistant ещё не было. Выводы о поведении облака опираются на код и
комментарии в нём.

**Границы этой редакции.** Разобраны 17 модулей Python (включая
`__init__.py`), `manifest.json`, `strings.json` и `services.yaml`. В выборке не
было `translations/*.json`, `hacs.json`, `brand/`, `docs/`, `dashboards/`,
`tests/` проекта, `scripts/` и workflow CI. Всё, что зависит от них, помечено
**«не перепроверялось»** и перенесено из редакции от 23 октября как есть.

## 1. Кратко

Интеграция остаётся зрелой для кастомного проекта. Все 14 исправлений P0 из
1.4.0 подтверждены кодом, а изменения 1.4.6 прошли проверку на действующем
Home Assistant: регистрация нового контроллера, изменение параметров котла и
запись изменений в существующие профили работают.

**Что изменилось после редакции для 1.4.5:**

* **1.4.6** закрыла находки 43, 44, 45, 48, 49, 54, 57 и 58. Находка 36
  (`native_min = 1` у поля имени профиля) **откатилась**: пустой черновик имени
  при таком значении нарушал проверку состояния в Home Assistant, и обе
  сущности `text.*_profile_name` не добавлялись. Находка 36 остаётся открытой.
* **1.4.7** добавляет работу с несколькими серверами (`app.reglerpro.ru` и
  `web.reglerpro.ru` с общими логином, паролем и номером дома): автоматический
  переход при сбое, безопасный для команд-переключателей (раздел 3.5).
* **1.4.8** добавляет в настройки шаг «Серверы»: основной и запасные адреса,
  проверка каждого сервера под вашей учётной записью, отключение перехода.
  Список читается из `entry.options` в `__init__.py` (находка 68 закрыта).
  Попутно исправлено: шаг «Параметры» при сохранении интервала опроса стирал
  остальные настройки.

**Главные риски на 1.4.7:**

1. **Облако отдаёт «успех» там, где его нет** (28, 17): неожиданный ответ
   `get_all_dev` превращается в пустой список, неверный пароль неотличим от
   прочих ошибок, reauth нет. Переход между серверами эту проблему не решает:
   он срабатывает на сбои сервера, но не на ошибки данных или авторизации.
2. **Идентификатор датчика не проверяется** ни в ответе `add_device`, ни в
   `tstatDtId` импортированного профиля климата (46, 47).
3. **Применение профиля климата** может записывать режим и температуру при
   выключенном климате (55): результат виден только как «не подтверждено».
4. **Экспорт `to_www` публикует файл без авторизации** (61).
5. **Формальный статус Quality Scale завышен** в первой редакции: нет
   `PARALLEL_UPDATES`, `runtime_data`, тестов config flow (раздел 4).
6. **Службы регистрируются из `async_setup_entry`** (подтверждено по
   `__init__.py`): нарушение правила `action-setup` (раздел 4, находка 70).

Накопленные открытые находки 1.4.0 (бинарные сенсоры, английские значения
состояний, `runtime_data`, reauth) по-прежнему ждут 1.5.0 / 2.0.

## 2. Что сделано хорошо

| Решение | Почему это важно |
|---|---|
| `DataUpdateCoordinator`, параллельный опрос контроллеров с изоляцией ошибок | единая точка опроса, `last_update_success` |
| `params_parser` | два формата, `None` вместо ложного нуля, защита от NaN и мусора |
| `climat_on_off` как переключатель: данные обновляются перед командой, команды идут под `asyncio.Lock` | команда не повторяется вслепую |
| Профили: схема v2 с миграцией из v1, очистка имён и значений (`clean_*`), проверка диапазонов и шага, потолок 20 профилей на тип | устойчивость к повреждённым и чужим файлам |
| Запись расписания: понижения по возрастанию периодов, повышения по убыванию; после ошибки группа времени блокируется | порядок «P1 < P2 < P3 < P4» не нарушается на промежуточных шагах |
| Откат (`undo`) и проверка результата (`_verify`) с отчётом `applied / failed / unverified / skipped` | пользователь видит, что реально применилось |
| Блокировка на контроллер при применении профиля, предварительный `async_refresh` и проверка `mqtt_online` | нет гонки профилей котла и климата |
| Импорт: имя файла только из каталога `kotel_profiles`, лимит 1 МБ, до 200 профилей, разрешение конфликтов `rename / overwrite / skip` | защита от обхода каталога и перегрузки |
| Загрузка файла: копия в каталог профилей выполняется в executor, при ошибке разбора файл удаляется | нет мусора после неудачной загрузки |
| Регистрация датчика требует явного подтверждения (`confirm`) | необратимое действие на сервере не срабатывает случайно |
| Нормализация `mqtt_online`, `None` вместо ложных значений (`tstatNow`, `korect_`, `sost_rab`) | нет «выдуманных» состояний |
| Работа с несколькими серверами: чтение повторяется на другом сервере, запись — только если запрос заведомо не дошёл; `climat_on_off` не удваивается | переход между серверами не инвертирует переключатели |
| Данные для решений «включить/выключить» берутся только после успешного обновления с признаком `detail_ok` | команда не отправляется по деградированным данным |
| Отсутствие внешних зависимостей, единый `KotelEntity`, `has_entity_name`, 114 переводимых сущностей | единообразие и меньше точек отказа |

## 3. Находки

Приоритеты: **P0** — ошибка или обещание, ломающее доверие или безопасность;
**P1** — стандарт HA и заметный UX; **P2** — качество и развитие;
**P3** — косметика. Нумерация сохранена из прошлой редакции (1–42), новые
находки продолжают её (43–70).

### 3.5. Работа с несколькими серверами (1.4.7)

Серверы `app.reglerpro.ru` и `web.reglerpro.ru` отдают одну и ту же учётную
запись. Клиент API (`api.py`) работает с одним из них, запоминает рабочий и на
основной возвращается не чаще раза в 10 минут. Правила рассчитаны на то, что
часть команд — переключатели, и повтор уже выполненной команды их инвертирует.

| Ситуация | Чтение (`get_*`) | Запись (команды, `add_device`) |
|---|---|---|
| нет соединения, DNS, сертификат | другой сервер | другой сервер (запрос не дошёл) |
| таймаут после отправки | другой сервер | **ошибка, повтор не выполняется** |
| ответ 5xx | другой сервер | **ошибка, повтор не выполняется** |
| ответ не в JSON | другой сервер | **ошибка, повтор не выполняется** |
| ответ 4xx (доступ, данные) | ошибка | ошибка |

Остальное: тайм-аут соединения 5 с (общий — 15 с); все серверы недоступны —
одна ошибка с причиной по каждому адресу; адрес не из `KNOWN_SERVERS`
используется как единственный. Запись и профили не дублируют команды ни при
каком сбое сервера, но и не гарантируют доставку: при «результат неизвестен»
пользователь видит ошибку, а проверку результата делает профиль (`_verify`).

**Настройка.** «Настройки → ReglerPro → Серверы»: основной сервер, список
запасных (по умолчанию второй из `KNOWN_SERVERS`), флажок «Сохранить без
проверки». При сохранении каждый сервер опрашивается отдельно под вашей учётной
записью; недоступный сервер блокирует сохранение и называется в ошибке. Пустой
список запасных отключает переход. Изменения применяются перезагрузкой записи
(слушатель параметров). Если ключа `fallback_urls` в параметрах нет, действует
автоматический режим 1.4.7.

Учётная запись больше не привязана к адресу: повторное добавление того же
логина и дома через другой сервер отклоняется как дубль, в том числе
относительно записей, созданных до 1.4.7. Не проверено на живом Home Assistant;
не охвачено автотестами: поведение при повторяющихся сбоях на обоих серверах
и поведение `aiohttp.ClientSession` с разными доменами (куки хранятся
отдельно для каждого домена, логин и пароль передаются в каждом запросе).
