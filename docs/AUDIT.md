# Аудит интеграции ReglerPro Controller для Home Assistant

**Дата редакции:** 13 ноября 2026 (предыдущая редакция — 23 октября 2026)  
**Версия на входе первого аудита:** 1.3.1  
**Версия, к которой относится эта редакция:** 1.4.5 (`manifest.json`)  
**Предмет:** `custom_components/kotel`.  
**Метод:** статический разбор кода, сверка `strings.json` и `services.yaml`
с кодом, проверка компиляции Python. Живой Home Assistant и облако ReglerPro
не использовались: выводы о поведении сервера опираются на код и комментарии
в нём.

**Границы этой редакции.** Разобраны 16 модулей Python, `manifest.json`,
`strings.json` и `services.yaml`. В выборке не было `__init__.py`,
`translations/*.json`, `hacs.json`, `brand/`, `docs/`, `dashboards/`,
`tests/`, `scripts/` и workflow CI. Всё, что зависит от них, помечено
**«не перепроверялось»** и перенесено из редакции от 23 октября как есть.

## 1. Кратко

Интеграция остаётся зрелой для кастомного проекта. Все 14 исправлений P0 из
1.4.0 подтверждены кодом 1.4.5. Менеджер профилей (`profiles.py`) стал самым
продуманным модулем: схема данных с миграцией, разделение профилей котла и
климата, безопасный порядок записи расписания, откат, проверка результата,
ограничения на импорт.

Со времени прошлой редакции в коде появились функции, которых в ней не было:

* регистрация нового датчика температуры из окна настроек (`add_device`);
* загрузка файла профилей извне (`FileSelector`) и экспорт в `/config/www`;
* раздельные профили котла и климата (`kind`), `rename_profile`,
  фильтрация расписания по активному режиму, блокировка на контроллер;
* повторная проверка записанных значений (каждые 4 с, до 20 с).

Какая именно версия 1.4.2–1.4.5 что принесла, по файлам установить нельзя:
`RELEASE_NOTES` в выборке не было.

**Главные риски на 1.4.5:**

1. **Пустой или «деградированный» ответ облака выглядит как успех.**
   `get_all_dev` с неожиданным ответом превращается в `[]`, а
   климат-переключатель `climat_on_off` принимает решение по таким данным и
   может выключить работающий климат (находки 28, 43).
2. **Раздувание базы рекордера.** Сводный сенсор `diagnostics` включён по
   умолчанию и пишет в атрибуты весь `params`, `params_raw` и данные климата;
   атрибуты меняются на каждом опросе (45).
3. **Пропущена зависимость `file_upload` в `manifest.json`** — загрузка
   файла может не работать, а `hassfest` её отклонит (44).
4. **Идентификатор датчика не проверяется:** ни ответ `add_device`, ни
   `tstatDtId` из импортированного профиля (46, 47).
5. **Окно настроек не переводится** в части подписей, зашитых в Python, и в
   `strings.json` нет `config.abort` (48).
6. **Формальный статус Quality Scale завышен** в прошлой редакции:
   `parallel-updates` отмечен ✅ ошибочно, `inject-websession` под вопросом
   (раздел 4).

Накопленные открытые находки 1.4.0 (бинарные сенсоры, английские значения
состояний, `runtime_data`, reauth) по-прежнему ждут 1.5.0 / 2.0.

## 2. Что сделано хорошо

| Решение | Почему это важно |
|---|---|
| `DataUpdateCoordinator`, параллельный опрос контроллеров с изоляцией ошибок | единая точка опроса, `last_update_success` |
| `params_parser` | два формата, `None` вместо ложного нуля, защита от NaN и мусора |
| `climat_on_off` как переключатель: данные обновляются перед командой, команды идут под `asyncio.Lock` | команда не повторяется вслепую |
| Профили: схема v2 с миграцией из v1, очистка имён и значений (`clean_*`), проверка диапазонов и шага, потолок 20 профилей на тип | устойчивость к повреждённым и чужим файлам |
| Запись расписания: понижения по возрастанию периодов, повышения по убыванию; после ошибки группа времени блокируется | порядок «P1 < P2 < P3 < P4» не нарушается на промежуточных шагах |
| Откат (`undo`) и проверка результата (`_verify`) с отчётом `applied / failed / unverified / skipped` | пользователь видит, что реально применилось |
| Блокировка на контроллер при применении профиля, предварительный `async_refresh` и проверка `mqtt_online` | нет гонки профилей котла и климата |
| Импорт: имя файла только из каталога `kotel_profiles`, лимит 1 МБ, до 200 профилей, разрешение конфликтов `rename / overwrite / skip` | защита от обхода каталога и перегрузки |
| Загрузка файла: копия в каталог профилей выполняется в executor, при ошибке разбора файл удаляется | нет мусора после неудачной загрузки |
| Регистрация датчика требует явного подтверждения (`confirm`) | необратимое действие на сервере не срабатывает случайно |
| Нормализация `mqtt_online`, `None` вместо ложных значений (`tstatNow`, `korect_`, `sost_rab`) | нет «выдуманных» состояний |
| Отсутствие внешних зависимостей, единый `KotelEntity`, `has_entity_name`, 114 переводимых сущностей | единообразие и меньше точек отказа |
