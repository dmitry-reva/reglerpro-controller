# Климат-контроль контроллера ReglerPro: возможности и настройка

Документ описывает, как устроен климат-контроль (термостат) в облаке ReglerPro, какие команды и данные для него существуют и как они отражены в интеграции Kotel для Home Assistant.

**Источники:** `climate.js` и `functions.js` (код веб-приложения), HAR-запись реальных ответов сервера (`get_big_contr`, `get_big_contr_climat`), подтверждения владельца системы (`tstatNow = 1` означает охлаждение; команды из интеграции выполняются успешно).

> **Условные обозначения.** ✅ — подтверждено реальным ответом сервера. 📄 — следует из кода приложения (`climate.js` / `functions.js`), но реального ответа в записи нет. ❓ — не подтверждено.

---

## 1. Принцип работы

Климат-контроль управляет котлом по температуре **помещения**, а не по температуре воды:

1. Пользователь выбирает **датчик температуры** помещения (устройство типа `dt`).
2. Задаёт **целевую температуру**: постоянную или по **расписанию** (до 4 периодов в сутки).
3. Контроллер сравнивает температуру датчика с целью и выставляет признак **`tstatNow`** (в `params`, индекс 25):

| `tstatNow` | Смысл (в приложении) |
|---|---|
| `0` | 🔥 нагрев |
| `1` | ❄️ охлаждение (подтверждено владельцем) ✅ |

Приложение показывает этот признак только когда климат-контроль включён **и** выбран датчик. Это условие `tstatOn && tstatDtId`; в интеграции оно названо `active`.

## 2. Формат запросов API

Все команды отправляются методом `POST` на `/php/taptop.php` в формате JSON. Параметры одинаковы для чтения и записи ✅:

| Поле | Назначение |
|---|---|
| `action` | название действия |
| `id_name` | идентификатор контроллера |
| `climat_war1` | **значение команды** (режим, ключ параметра, id датчика) |
| `range` | числовое значение (для `range_climat`; в остальных командах не используется) |
| `userId` | идентификатор дома |
| `login`, `password` | учётные данные |

Пример (учётные данные скрыты):

```json
{
  "climat_war1": "",
  "action": "get_big_contr_climat",
  "range": 45,
  "userId": "<ID дома>",
  "id_name": "<ID контроллера>",
  "login": "***",
  "password": "***"
}
```

> Приложение в поле `range` отправляет последнее значение слайдера (в записи — `45`), независимо от действия. Интеграция отправляет `0`: для команд, не использующих `range`, это не имеет значения.

### Действия климат-контроля

| Действие | `climat_war1` | `range` | Что делает | Ответ |
|---|---|---|---|---|
| `get_big_contr_climat` | пусто | — | данные контроллера с климатом | `{ "contr": {...}, "sensors": [...] }` ✅ |
| `climat_on_off` | пусто | — | **переключает** климат-контроль вкл↔выкл | `{contr, sensors}` 📄 |
| `mode_klimat` | `0`, `3`, `4` или `5` | — | выбирает режим | не используется приложением 📄 |
| `range_climat` | имя параметра | значение | записывает температуру или час | не используется приложением 📄 |
| `get_climat_sensors` | пусто | — | список датчиков для выбора | `{contr, sensors}` 📄 |
| `select_climat_sensors` | `id_name` датчика | — | выбирает датчик | `{contr, sensors}` 📄 |

Нюансы:

- **`climat_on_off` — переключатель, а не «установить».** Явного значения «включить»/«выключить» у команды нет, поэтому её нельзя повторять вслепую: решение «включать или выключать» нужно принимать по свежему состоянию.
- В ответе `get_big_contr_climat` список `sensors` оказался **пустым** ✅, хотя датчик выбран. Список для выбора, по коду приложения, возвращает `get_climat_sensors`; в записи его нет.
- Формат ответов на команды записи (`mode_klimat`, `range_climat`) приложение не использует: после команды оно просто заново читает данные контроллера.

## 3. Данные климат-контроля в ответе контроллера

### 3.1. `tstatArr`

Поле приходит **строкой с JSON** ✅. Пример реального значения:

```json
{
  "tstatDtId": "<ID датчика>",
  "tstatOn": 1,
  "tstatTemp": 24,
  "m3_P1_time": 0,  "m3_P2_time": 6,  "m3_P3_time": 12, "m3_P4_time": 18,
  "m3_P1_temp": 25, "m3_P2_temp": 25, "m3_P3_temp": 25, "m3_P4_temp": 25,
  "tstat_mode": 0
}
```

| Поле | Значение |
|---|---|
| `tstatOn` | климат-контроль включён (`1`/`0`) |
| `tstat_mode` | режим: `0`, `3`, `4`, `5` (см. раздел 4) |
| `tstatTemp` | целевая температура режима 0 |
| `tstatDtId` | `id_name` выбранного датчика |
| `m3_*`, `m4_*`, `m5_*` | значения расписания (раздел 5) |

> ❓ В реальном ответе присутствуют **только ключи `m3_*`**. Ключей `m4_*` и `m5_*` сервер пока не вернул (вероятно, они появляются после первой записи). Приложение для отсутствующих значений показывает «undefined».

### 3.2. Прочие поля контроллера, связанные с климатом

| Поле | Пример | Смысл |
|---|---|---|
| `tempUstNowTstate` | `{"period": 0, "temp": 24}` | **актуальная** цель с учётом текущего периода ✅ |
| `temp_dt_ust` | `24` | цель (дублирует `temp`) ✅ |
| `textPeriodOn` | `""` | подпись активного периода ✅. Лежит **на верхнем уровне** ответа, а не внутри `tempUstNowTstate` |
| `sensor_name` | `"Холл"` | имя выбранного датчика ✅ |
| `sensor_temp` | `"24"` | температура датчика (**строка**) ✅ |
| `params[25]` | `1` | `tstatNow` ✅ |

> В режиме 0 `tempUstNowTstate.period` равно `0`. Значение `period` и формат `textPeriodOn` в режимах расписания ❓ не проверялись: в записи только режим 0.

### 3.3. Индексы `params`, относящиеся к климату

В формате JSON-массива (30 элементов в наблюдаемой прошивке) климату принадлежат:

| Индекс | Ключ | Комментарий |
|---|---|---|
| 25 | `tstatNow` | `0` нагрев / `1` охлаждение ✅ |
| 30 | `klimat_max` | ❓ в наблюдаемой прошивке отсутствует |
| 31 | `klimat_min` | ❓ в наблюдаемой прошивке отсутствует |

Назначение `klimat_max` и `klimat_min` по имени неочевидно, в приложении они не используются.

## 4. Режимы климат-контроля

| `tstat_mode` | Название | Как задаётся цель |
|---|---|---|
| `0` | Постоянная температура | одно значение `tstatTemp` |
| `3` | Расписание **7/7** | один набор из 4 периодов на всю неделю |
| `4` | Расписание **5/2** | отдельные наборы для **ПН–ПТ** и для **СБ–ВС** |
| `5` | Расписание **4/1/2** | отдельные наборы для **ПН–ЧТ**, **ПТ** и **СБ–ВС** |

Выбор режима выполняется командой `mode_klimat` с кодом режима в `climat_war1`.

---

## 5. Расписание

В каждом наборе **4 периода** (`P1`…`P4`). У периода два параметра:

- **`time`** — час начала периода, целое число **0–23**;
- **`temp`** — температура периода, **5–40 °C с шагом 0,5** 📄.

### 5.1. Ключи

Шаблон ключа: `m<режим>_P<период>_[<день>_]<time|temp>`.

| Режим | Дни | Шаблон ключа | Пример |
|---|---|---|---|
| 3 (7/7) | ПН–ВС | `m3_P{n}_{kind}` | `m3_P2_time` |
| 4 (5/2) | ПН–ПТ | `m4_P{n}_d5_{kind}` | `m4_P1_d5_temp` |
| 4 (5/2) | СБ–ВС | `m4_P{n}_d2_{kind}` | `m4_P3_d2_time` |
| 5 (4/1/2) | ПН–ЧТ | `m5_P{n}_d4_{kind}` | `m5_P2_d4_time` |
| 5 (4/1/2) | ПТ | `m5_P{n}_d1_{kind}` | `m5_P4_d1_temp` |
| 5 (4/1/2) | СБ–ВС | `m5_P{n}_d2_{kind}` | `m5_P1_d2_temp` |

Всего **6 наборов × 4 периода × 2 параметра = 48 значений**.

### 5.2. Правила для времени начала периодов

Приложение ограничивает слайдер времени по соседним периодам 📄:

| Период | Минимум | Максимум |
|---|---|---|
| P1 | `0` | время P2 − 1 |
| P2, P3 | время предыдущего + 1 | время следующего − 1 |
| P4 | время P3 + 1 | `23` |

Следствие: часы всегда идут строго по возрастанию, например `0 → 6 → 12 → 18`. Периоды всегда четыре; «выключить» период нельзя.

### 5.3. Запись значения

Одно значение отправляется одной командой:

```json
{ "action": "range_climat", "climat_war1": "m3_P1_temp", "range": 22.5, "id_name": "<ID контроллера>", "userId": "<ID дома>", "login": "***", "password": "***" }
```

Для постоянной температуры используется тот же `range_climat`, а ключ равен **`temp_dt`**.

---

## 6. Выбор датчика

1. `get_climat_sensors` возвращает список элементов вида `{ "id_name": "...", "name": "..." }` 📄.
2. `select_climat_sensors` с `climat_war1 = <id_name>` выбирает датчик.
3. Выбранный датчик отражается в `tstatArr.tstatDtId`, его имя в `sensor_name`.

Датчик — это обычное устройство типа `dt`, которое уже есть в `get_all_dev` (`temp`, `time`).

## 7. Как это отражено в интеграции Kotel

| Возможность | Сущность Home Assistant |
|---|---|
| Включение/выключение, режим, целевая температура | `climate` «Термостат» |
| Режимы расписания | пресеты термостата |
| Выбор датчика | `select` «Датчик климат-контроля» |
| Время и температура периодов | 48 `number` (категория «Конфигурация») |
| Текущий режим (нагрев/охлаждение) | сенсор «Климат-контроль» и `hvac_action` термостата |
| Данные климата, диагностика | сенсоры «Климат: …», «Диагностика параметров» |

### 7.1. Соответствие режимов

| Состояние контроллера | `hvac_mode` | Пресет |
|---|---|---|
| `tstatOn = 0` | `off` | — |
| включён, `tstat_mode = 0` | `heat` | — |
| включён, `tstat_mode = 3` | `auto` | «Расписание 7/7» |
| включён, `tstat_mode = 4` | `auto` | «Расписание 5/2» |
| включён, `tstat_mode = 5` | `auto` | «Расписание 4/1/2» |

`hvac_action`: выключен → `off`; включён без датчика → `idle`; `tstatNow = 0` → `heating`; `tstatNow = 1` → `cooling`.

### 7.2. Алгоритмы команд

- **Включить/выключить.** Сначала обновляются данные, и `climat_on_off` отправляется только если состояние отличается от нужного. Повторное «выключить» ничего не отправляет.
- **`heat`.** Включает климат (если выключен) и выбирает режим 0.
- **`auto`.** Включает климат (если выключен). Если текущий режим не расписание, выбирает режим 3.
- **Пресет.** Включает климат (если выключен) и выбирает режим 3, 4 или 5.
- **Температура.** Только в режиме 0: округляется до 0,5 °C, ограничивается 5–40 °C и отправляется как `range_climat` / `temp_dt`. В режиме расписания возвращается ошибка с подсказкой.
- Команды одного термостата выполняются строго по очереди, после каждой данные обновляются.

### 7.3. Примеры использования

Включить расписание 5/2:

```yaml
action: climate.set_preset_mode
target:
  entity_id: climate.kotel_kontroller_termostat   # ID у вас может отличаться
data:
  preset_mode: "Расписание 5/2"
```

Изменить начало второго периода в расписании 7/7:

```yaml
action: number.set_value
target:
  entity_id: number.kotel_kontroller_raspisanie_7_7_pn_vs_p2_nachalo
data:
  value: 7
```

Выключить климат-контроль, когда никого нет дома:

```yaml
automation:
  - alias: Kotel — климат выключается при отсутствии людей
    triggers:
      - trigger: state
        entity_id: zone.home
        to: "0"
        for: "01:00:00"
    actions:
      - action: climate.turn_off
        target:
          entity_id: climate.kotel_kontroller_termostat
```

## 8. Что не подтверждено

| Вопрос | Что известно |
|---|---|
| Ответы на `mode_klimat`, `range_climat` | в записи нет; интеграция после команд заново читает данные |
| Ключи `m4_*` и `m5_*` | в ответе сервера отсутствуют; не ясно, создаст ли сервер ключ при первой записи |
| Формат ответа `get_climat_sensors` | известен только из кода приложения |
| Значение `tempUstNowTstate.period` и текст `textPeriodOn` в режимах расписания | в записи только режим 0 |
| Назначение `klimat_max`, `klimat_min` | в наблюдаемой прошивке отсутствуют |
| Поведение при отсутствии датчика | не проверялось |

Если при проверке в режимах расписания значения окажутся иными, достаточно прислать записи ответов: разбор данных локализован в `coordinator.py` (функция `_parse_climate`).

---

## 9. Безопасность

HAR-файл содержит **логин и пароль открытым текстом** в каждом запросе. Перед отправкой таких записей третьим лицам удаляйте поля `login` и `password`; если файл уже передавался, смените пароль.
